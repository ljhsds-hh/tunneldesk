## 0. 背景

阶段一通读与一次真实使用暴露了两件事：

1. 走内网代理时 SVN `checkout` / `update` 正常、**`commit` 失败**，定位为 `server/src/proxy/httpProxy.ts` 的 HTTP/1.1 语义不合规（强制 `Connection: close`、一连接只解析一次请求头、请求行改写），破坏 WebDAV 写事务序列。
2. 端口映射的 B 侧防火墙规则**不判断目标地址归属**；当 `targetHost` 是「B 能访问到、但不属 B 本机」的第三方内网地址时，在 B 上开放端口没有意义，且会长期残留。

用户据此重新划定两条通道的职责：端口映射承担全部协议场景，内网代理收缩为纯 Web 浏览通道；并追加一项防火墙补修（下称 **F1**）。

本阶段的核心判断：**端口映射是协议无关的纯 TCP 裸转发**（`forward/manager.ts:182-183` 的 `socket.pipe(channel)` / `channel.pipe(socket)`），五项能力在协议层本就具备，本阶段不是新增五套协议栈，而是把已知适配问题处理或写清、补齐验证与使用说明、并完成 F1。

## 3. 功能需求

### FR-1 端口映射 · HTTP 全支持

- 现状：`net.createServer` 监听 `bindAddress:localPort`（`forward/manager.ts:100`），经 SSH `direct-tcpip`（`ssh/link.ts:107`）双向裸转发。
- 要求：保证 HTTP 请求/响应（含任意方法、任意 body、chunked、大响应）字节无损透传；不得因映射改变请求语义。
- 程序侧需处理/说明：映射到 `127.0.0.1:<端口>` 后 `Host` 头变化、服务端按虚拟主机路由、响应中返回原始内网绝对 URL 导致的重定向。
- 验收标准：本地起真实 HTTP 服务，经映射完成 GET / POST / 大响应 / chunked / 长响应；给出 A 侧 URL 写法与 hosts + 同端口的规避方式（第 6 章）。

### FR-2 端口映射 · HTTPS 全支持

- 要求：TLS 握手与加密流量完整透传，不解密、不做 MITM；SNI 与证书校验行为与直连一致。
- 程序侧需处理/说明：证书 SAN/SNI 与 `127.0.0.1` 不匹配时的客户端处理（信任例外或 hosts + 同端口），不得由程序自动改 hosts / 装证书（C4）。
- 验收标准：本地起自签 HTTPS 服务，经映射完成握手与请求；记录证书校验的两种处理路径。

### FR-3 端口映射 · Git 全操作

- 「全操作」在本阶段纳入验收的集合：`clone`、`fetch`、`pull`、`push`、`commit`、`branch`、`tag`、`merge`、`rebase`、`submodule`、`status` / `log` / `diff`，以及 **Git LFS** 的上传下载。
- 协议形态均须覆盖：`http(s)://` Smart HTTP、`ssh://` / `git@`、`git://`（皆为 TCP，转发层无需区分）。
- 要求：Smart HTTP 的服务端重定向、pack 大包传输、认证凭据交互、LFS 的批量上传均无损透传。
- 验收标准：**本机具备真实 `git` 客户端**，用本地裸仓库 / `git daemon` 跑通上述集合，标记为 `[local-real]`；其余形态标记为 `[mock]` 透传验证。

### FR-4 端口映射 · SVN 全操作

- 「全操作」集合：`checkout`、`update`、`commit`、`add`、`delete`、`copy`、`move`、`merge`、`switch`、`relocate`、`revert`、`status`、`diff`、`log`、`import`、`export`、`mkdir`、属性操作。
- 协议形态均须覆盖：`http(s)://` WebDAV、`svn://`（3690）、`svn+ssh://`。
- 要求：WebDAV 扩展方法（`PROPFIND` / `REPORT` / `MKACTIVITY` / `CHECKOUT` / `MERGE` 等）、有状态写事务、大文件上传均无损透传；**转发层不得像 `httpProxy.ts` 那样改写请求**（C1、C6）。
- 验收标准：本机无 `svn` / `svnserve`，只能做协议无关的 TCP 透传验证（字节完整性、事务期间连接复用、并发、大包、半关闭），标记 `[mock]`；真实操作由用户按第 8 章自测。
- 使用侧适配：工作副本记录绝对 URL，换到本地地址需一次 `svn relocate`；须给出可复制命令。

### FR-5 端口映射 · 数据库全操作（SQL Server / MySQL）

- 「全操作」集合：连接与认证、DDL（建/改/删库表、索引、约束、视图）、DML（增删改查、批量导入、多语句）、事务（`commit` / `rollback`）、存储过程与函数、大字段 BLOB / TEXT、长连接与连接池、大结果集流式读取。
- 覆盖：`SQL Server`（TDS，默认 1433）、`MySQL`（默认 3306），含各自的 TLS 加密连接。
- 要求：转发层不解析协议；须保证**长连接空闲保持**、大包双向、并发连接、半关闭语义无损。现有 SSH 参数为 `keepaliveInterval: 15000` / `keepaliveCountMax: 3`（`ssh/client.ts:45-46`），需验证长时间空闲会话不被断开。
- 若验证发现现有转发核心存在必须修改的缺陷，须**先回报用户并修订 C1**，不得静默改动。
- 验收标准：本机无 `mysql` / `mysqld` / `sqlcmd` / `psql` / `docker`，只能做协议无关 TCP 透传与长连接保持验证，标记 `[mock]`；真实操作由用户按第 8 章自测。
- 连接串须给出可复制示例：SQL Server 用 `host,port` 形式，MySQL 用显式 `--port`。

### FR-6 内网代理 · 仅 HTTP / HTTPS，零代码改动

- 保持 `httpProxy.ts` 现状：普通请求走绝对 URL 解析（`:215-269`），HTTPS 走 `CONNECT` 隧道（`:182-212`）。
- **本阶段不新增、不修复、不重构**：不做 SOCKS5、不做 UDP、不做任意端口 CONNECT 转发、不做 Git / SVN / 数据库专项支持、**不修第 0 章所述 HTTP/1.1 语义缺陷**。
- 规格须写明的已知限制：依赖连接复用或 WebDAV 扩展方法的客户端（含 SVN commit）经代理可能失败，此类场景一律改用端口映射；PAC 白名单只支持固定 IPv4 精确匹配，沿用 v0.2 行为。
- 验收标准：本地起 HTTP / HTTPS 服务，确认经 `:8888` 可访问；标注为「现状回归验证」而非新增能力。

### FR-7 端口映射 · F1 防火墙规则归属补修（必做）

## 4. F1 详细规格：B 侧防火墙规则按目标归属判定

### 4.1 现状与问题

| 位置 | 现状 |
| --- | --- |
| `app.ts:686` | desired 集合只筛 `mapping.enabled && mapping.syncFirewall`，**完全不看 `targetHost`** |
| `firewall/manager.ts:43-52` | 仅按 `syncFirewall` 判断（`:43`），**不看 `targetHost`**，即下发 `New-NetFirewallRule -Protocol TCP -LocalPort ${targetPort}`，入站 + 出站各一条 |
| `firewall/manager.ts:95-99` | `sync()` 把 desired 内但防火墙缺失的算 `missing`（补建），把防火墙有但 desired 没有的算 `orphans`（清理） |
| 默认值 | `syncFirewall: true`（`app.ts:576`、`api/server.ts:199`、`config/store.ts:120`、`Mappings.tsx:44`）；`targetHost` 默认 `127.0.0.1`（`app.ts:547`、`api/server.ts:196`） |
| 归属判定 | **全仓不存在**任何 loopback / 目标归属判断 |

结论：只要把目标地址改成 B 能访问到的第三方内网地址，B 上就会创建一条无意义的放行规则，且因它在 desired 集合内，对账会长期保留。

### 4.2 判定规则（用户拍板）

| `targetHost`（先 `trim()` 再 `toLowerCase()`） | 归属 | 是否在 B 上创建/保留规则 |
| --- | --- | --- |
| `localhost` | B 本机 | 是 |
| `127.0.0.1` | B 本机 | 是 |
| `::1` | B 本机 | 是（见 4.3 校验缺口） |
| 任何其它 IPv4（**含 B 自身内网 IP**、`127.0.0.2` 等 127/8 地址） | 非 B | **否** |
| 任何域名、B 的机器名、其它 IPv6 | 非 B | **否** |

- **严格按字面量白名单判定，不做 127/8 网段推断、不做 DNS 解析、不比对 `HostConfig.host`**。理由：Bastion 模式下端口被固定为 `BASTION_LOCAL_PORT = 50022`（`bastion/command.ts:3`、`config/store.ts:69`），主机地址是 `127.0.0.1:50022`（README 第 4 节），那是隧道端点而非 B 的真实内网 IP，程序拿不到可靠的 B 内网地址。
- `syncFirewall` 是「自动维护」开关，不是「归属」开关：关闭后已有规则保留，但不再自动创建 / 修复；判定为「非 B」时即便 `syncFirewall === true` 也不得创建规则。

### 4.3 既有校验缺口（实施必须一并处理）

`isValidHostname()`（`util/net.ts:50-59`）当前只接受字面量 `localhost`、IPv4 点分十进制、域名正则，**不接受 `::1`**（含冒号，两条正则均不命中）。因此若不改校验函数，用户填 `::1` 会在 `app.ts:553` / `:602` 被判「目标地址不合法」，4.2 的承诺无法兑现。

要求：为 `isValidHostname()` 增加 IPv6 回环白名单（至少 `::1`），并补对应单测。IPv6 回环在 B 侧是否可用属使用前提，须在说明中提示。

### 4.4 desired 集合、missing 与 orphans

定义：

```text
owned   = { 所有 targetHost ∈ {localhost, 127.0.0.1, ::1} 的映射 }   // 规则归属，决定是否清理
desired = { owned 中 syncFirewall = true 的映射 }                    // 自动维护集合，决定是否补建 / 修复
```

判定前必须先按 4.2 对 `targetHost` 做 `trim()` + `toLowerCase()` 规范化（例如 `LOCALHOST` 应等价于 `localhost`），不得直接拿原始字符串做字面量比较。

`enabled` **不参与**归属判定：停用映射只停止 A 侧监听，不删除 B 侧规则；重新启用时也不需要重建规则。

`syncFirewall` **不参与**归属判定：关闭同步表示「规则保留，但我不再自动维护」，只有删除映射或目标改为非 B 才清理。因此关闭同步后手工修好的规则不会被对账覆盖，重新打开同步时再按期望重建 / 补建。

| 情形 | 分类 | 动作 |
| --- | --- | --- |
| 映射在 desired 内、B 上没有对应规则 | `missing` | **补建**，不清理 |
| 映射在 desired 内、但规则端口 / 方向 / 协议 / 启用状态与期望不一致 | `stale` | **重建**（先删同名规则再建入站 + 出站） |
| 映射在 owned 内但不在 desired 内（关闭同步）、B 上有对应规则 | `kept` | **保留**，不补建、不修复、不清理 |
| 映射不在 owned 内（从未配置 / 已删除 / 目标改为非 B）、B 上却有带 `TunnelDesk-` 前缀的规则 | `orphans` | **清理** |

- 判据是「规则名不在当前 owned 集合」，**不是「没人用」**——Windows 防火墙规则没有引用计数或可靠的最后命中时间，`Get-NetFirewallRule` 不返回此类信息，不实现基于「使用状态」的判定。
- `sync()` 不能只比较规则名：`list()` 同时读取 `LocalPort` / `Protocol` / `Enabled`，端口改动、只存在单方向、协议被改、规则被禁用都会触发重建。这样即使改端口时 SSH 离线、旧规则没能立即删除，重连后的对账也能修正。
- 清理范围：仅 `RULE_PREFIX = 'TunnelDesk-'` + `RULE_GROUP = 'TunnelDesk'`。现有 `list()` 已按 `Group` 枚举再本地过滤，别人建的规则即使闲置也不进入视野（C2、C3）。

### 4.5 对账时机

| 时机 | 现状 | 本阶段 |
| --- | --- | --- |
| 新建 / 编辑 / 删除映射 | `app.ts:585` / `:635` / `:650` 已调 `syncFirewall()` | 保持 |
| SSH 上线 / 重连 | `handleOnline()`（`app.ts:720-732`）已调 `syncFirewall()` | 保持，作为上线 / 重连时强制对账 |
| 手动「立即对账」 | `POST /api/firewall/sync`（`api/server.ts:251-252`） | 保持 |
| **低频兜底** | 无 1 小时级兜底（现有 `ticker` 每秒只算速率：`app.ts:153` 注册、`:158` 清理、`:734-752` 为 `tick()` 实现） | **新增 1 小时定时兜底**，覆盖程序崩溃 / 断电后遗留的规则 |

兜底要求：

- 仅在 `link.isOnline()` 时执行，离线直接跳过；
- 与配置变更触发的对账**互斥串行化**，不得并发下发 PowerShell（避免新建映射中途被误判为孤儿）；
- 频率固定 1 小时，**不做 5 分钟**（每次需 SSH exec 枚举全部防火墙规则，Windows 上可能耗时数秒，5 分钟为无谓开销与日志噪声）；
- 参照现有 `ticker`（`app.ts:153` / `:158`）的生命周期管理：程序退出时清理定时器，重连不叠加多个定时器。

### 4.6 UI 与后端兜底

- `Mappings.tsx:359` 的「B 侧目标地址」提示改为明确说明：仅 `localhost` / `127.0.0.1` / `::1` 视为 B 本机会同步防火墙；填 IP 或域名时不创建 B 侧规则。
- `Mappings.tsx:376-386` 的「在 B 上同步防火墙规则」开关：当 `targetHost` 判定为「非 B」时置为不可用并给出原因，避免用户误以为已开启。
- **后端必须硬校验兜底**：`app.ts` 的 `createMapping` / `updateMapping` 与 `firewall/manager.ts` 的 `applyMapping` 都要阻止为非 B 目标创建规则，不能只靠 UI 禁用（防止直接调用 REST API 绕过）。
- 置灰的开关**不提供「仍要同步」之类的手动绕过入口**；判定为「非 B」即强制不同步，与上一条后端校验共同保证规则一致性。

### 4.7 已知副作用（用户已确认接受）

- 存量配置中 `targetHost` 填 B 自身内网 IP 的映射，将失去 B 侧防火墙同步，其历史规则会在下一次对账中被当 `orphans` 清掉；若该场景确实需要放行，用户须改用 `127.0.0.1` 或自行在 B 上手动建规则。
- 第三方目标主机自身的防火墙不在本工具职责内：能访问就访问，不能访问就不访问，**不得代为修改**（C2）。

## 6. 已知限制与使用侧适配（须写进使用说明）

| 项 | 说明 | 由谁处理 |
| --- | --- | --- |
| HTTPS 证书 SAN / SNI | 映射到 `127.0.0.1:<端口>` 后与证书主机名不符 | 否（C4），给出信任例外或 hosts + 同端口方案 |
| `Host` 头与虚拟主机 | HTTP 服务端按 Host / server_name 路由时可能返回 404/400 | 否，给出 hosts + 同端口方案 |
| 服务端绝对 URL 重定向 | Git Smart HTTP、WebDAV `Destination` / `Location` 会指回原始内网域名 | 否，给出 hosts + 同端口方案 |
| SVN 工作副本 URL | 记录绝对地址，换地址需 `svn relocate` | 否，给出可复制命令 |
| 数据库 TLS 证书 | SQL Server 强制加密 / MySQL TLS 会校验证书主机名，与 `127.0.0.1` 不符 | 否，给出信任配置或 hosts + 同端口方案 |
| SQL Server 命名实例 | `HOST\INSTANCE` 走 UDP 1434，不支持 | 否（NT-4），须 `host,port` 显式端口 |
| 长连接空闲 | 数据库会话可能长时间无数据，需验证 SSH keepalive 与 channel 生命周期 | 程序（FR-5 验证项）|
| 本地端口 ≠ 远端端口 | 所有 URL / 连接串需同步改端口 | 否，给出写法示例 |
| PAC 白名单 | 只支持固定 IPv4 精确匹配、单次最多 200 个 | 沿用 v0.2，不在本阶段变更 |

> 「全完成」的口径：**协议与链路层能力完备、已知适配项全部处理或写明、使用说明齐全**；应用层的主机名 / 证书 / URL 适配属用户侧一次性配置，不算程序缺陷。

## 11. 实施后修订记录（2026-11-10）

实施与验证中发现多处需要修订的需求侧表述，均**未扩大范围、未改转发核心**：

1. **FR-5「半关闭语义无损」→「半关闭后连接干净回收」**。验证发现 `socket.pipe()` 的 end 级联会让「客户端发完数据立即 FIN 写方向、仍期待回包」丢失回包；用纯 `net` 两层代理可复现，属 Node pipe 固有行为而非 TunnelDesk 缺陷，且 HTTP / WebDAV / TDS / MySQL / Git 均在收到响应后才关闭，不受影响。曾尝试把 `channel.on('close')` 的 `destroy()` 改为 `end()`，验证**未解决问题**，已回退；`forward/manager.ts` 转发核心保持零改动，**C1 未被修订**。测试改为验证连接被干净回收、不泄漏。
2. **FR-3 的 `[local-real]` Git 范围收窄**。本机 PortableGit 无 `git-daemon` / Smart HTTP 服务端，完整 clone / push 无法在本地起真实 Git 服务；改为「真实 git 客户端生成的二进制流经映射完整性验证」，完整操作交由 V-3 真实环境验收。
3. **收尾代码审核（23:20）发现并修复一处并发缺口**：`removeMapping()` 原先直接下发远端命令、绕过 `syncFirewall()` 的串行链，定时兜底与配置变更仍可能并发。已抽出统一的 `enqueueFirewall()`，删除/改端口的规则清理、对账、1 小时兜底全部走同一条链，并补了对应单测（76 → 77 项）。同时删除验证脚本里一条恒真的假阳性检查（他人规则是否受影响本就无法由 mock 断言，改由真实环境 V-10 步骤 4 覆盖），并清理死常量与非 JSON 响应解析。随后补了 4 类运行时边界检查：`::1` 目标建规则、大小写与空格规范化、第三方改回 B 本机后规则补建、删除第三方映射不报错。
4. **2026-11-11 复审修订**：明确「停用映射 / 关闭同步都保留规则，只有删除映射或目标改为非 B 才清理」；新增 `firewallOwned()` 只按 `targetHost` 判定归属，`firewallEligible()` 只决定是否自动补建 / 修复；`sync()` 从按规则名比对升级为按名称 + 本地端口 + 方向 + 协议 + 启用状态比对，修复 SSH 离线改端口后旧规则无法回收、单方向缺失不补建的问题；修正映射卡片「防火墙同步」误报与 B 侧规则禁用仍显示「已放行」的 UI 问题。测试数 85，本地验证 27 项。

另：为消除多 worker 并发写临时缓存的环境冲突，`server/package.json` 的 `test` 脚本固定为单 worker（`--pool=forks --maxWorkers=1 --minWorkers=1`），不改变任何业务配置（C8 保持）。
